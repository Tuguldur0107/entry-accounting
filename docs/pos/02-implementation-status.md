## eBarimt 3.0 — товч

Дэлгэрэнгүй: `03-ebarimt-integration-plan.md` (дизайн), `docs/deployment/ebarimt.md`
(нэвтрүүлэлт). Гол зарчим:

- PosAPI 3.0 нь **мерчантын талын үйлчилгээ** — Entry HTTP-ээр дууддаг.
  `server` горим (Railway-ийн `posapi` service, зөвлөж буй) эсвэл `browser`
  горим (кассын PC-ийн localhost, кассын дэлгэц өөрөө илгээнэ)
- Борлуулалт батлагдмагц `pos_ebarimt_submissions` дараалалд орж **async**
  илгээгдэнэ — борлуулалт ХЭЗЭЭ Ч хүлээхгүй, илгээлтээс болж зогсохгүй
- ДДТД / сугалаа / QR ирмэгц баримтад гарна; амжилтгүй бол backoff + 3
  дараалсан алдаанд мэдэгдэл; зассаны дараа гараар [Дахин илгээх]
- Буцаалт → эх ДДТД цуцлагдаж, үлдсэн мөрөөр шинэ баримт
- **Код ЗОХИОХГҮЙ:** барааны ангилал (7 орон), татварын бүтээгдэхүүний код
  (3 орон), төлбөрийн хэлбэрийн eBarimt код дутвал баримт илгээгдэхгүй,
  шалтгаан нь UI-д ил (`[EBARIMT_*]`)
- **Борлуулалт бүрд eBarimt-гүй явуулах:** төлбөрийн диалогийн «eBarimt баримт
  илгээх» switch (default асаалттай; унтраавал худалдан авагчийн блок нуугдана)
  → `pos_sales.ebarimtStatus = "skipped"`, дараалалд орохгүй, жагсаалтад
  «eBarimt илгээгээгүй» chip, панелиас [eBarimt илгээх]-ээр дараа илгээнэ;
  AI `create_pos_sale.skipEbarimt`. Хуулийн үүрэг кассчны хариуцлагад — аудитын
  хураангуйд ил
- **Бэлэн байдлын шалгалт (`lib/ebarimt/readiness.ts`, ЦЭВЭР+тесттэй):** дээрх
  дутууг switch АСААХААС ӨМНӨ тоолж нэрлэнэ (бүлгээс өвлөсөн код тооцогдоно) —
  UI-д блок + server талд `updatePosSettings` хориг + `get_ebarimt_status`
- **v2 (2026-09-20, албан баримттай тулгасан):** операторын төвлөрсөн PosAPI
  (нэг суулгац, олон мерчант); **сугалаа/QR ХАДГАЛАГДАХГҮЙ** — борлуулалтын мөчид
  ≤8 сек хүлээж нэг удаа хэвлэнэ, дахин хэвлэхэд ДДТД; **хэсэгчилсэн буцаалт
  `inactiveId` гинжээр** (сугалаа дахин олгохгүй), бүтэн буцаалт DELETE;
  `/rest/info`-оос сугалааны нөөц / ТЕГ рүү илгээлтийн хоцролт / PosAPI хүрэлцээ
  → самбар + мэдэгдэл; татварын кодын албан лавлах (3 орон) сонгогч

## QPay — товч

```
Холбох: [QPay холбох] → dashboard (бүртгэл/онбординг/consent) → callback?state&code → сервер-сервер exchange
        → key/secret шифртэй + «QPay» хэлбэр/түр данс автомат → асна (гар зам: key хуулах хэвээр)
QPay мөр сонгов → [QR үүсгэх] → pos_qpay_intents (open, cartSnapshot) → dashboard POST /api/v1/invoices
   → QR + deeplink → диалог Entry DB-ээс 2 сек тутам (QPay polling ҮГҮЙ — ККТТ хориг)
   ← webhook payment.paid (HMAC) ЭСВЭЛ [Шалгах] (10 сек-д нэг) → paid
→ Төлбөр авах → createPosSale({ qpayIntentId }) → транзакцад finalized
   унавал → paid & saleId null → жагсаалтын баннер [Борлуулалт болгох] (snapshot-оос) / 10 мин → мэдэгдэл
```

- GL ӨӨРЧЛӨЛТГҮЙ: `ewallet` хэлбэрийн түр данс (банкны хуулгаар тэгшитгэнэ, 1% шимтгэл settlement-д)
- **Settlement автомат (2026-09-25):** банкны хуулгын импорт QPay-ийн шилжүүлгийг түр дансны
  тулгагдаагүй орлогуудтай FIFO-оор тулгаж санал болгоно (`lib/cash/ewallet-settlement.ts`);
  «Ашиглах» / MCP `ewalletSettlement: true` → түр данс → банк шилжүүлэг (цэвэр) + шимтгэлийн
  зарлага (`pos_settings.ewalletFeeAccountNumber`, default 73100008). Шимтгэл = нийт − цэвэр
  (хуулгаас), хэлбэрийн `feePercent` нь тулгалтад л
- Нууц (API key, webhook secret) `encryptSecret`-ээр, `getQpayStatus` зөвхөн `*Set: boolean`;
  `/api/health.qpay` зөвхөн тоолуур
- Буцаалт QPay-ээр ҮГҮЙ (Quick QR refund-гүй) — бэлэн / дэлгүүрийн кредит

## Мэдэгдэж буй хязгаарлалт

- Төлбөрийн диалог Төлсөн/Үлдэгдэл/Хариултыг локал бодно — эцсийн шалгалт server `planPayments`
  (`[APPROVAL_REQUIRED]`, `[NEGATIVE_STOCK]`, `[CREDIT_LIMIT]` алдаа тэр чигээрээ харагдана).
- Борлуулалтын жагсаалтад баримт бүрийн COGS багана байхгүй (мөр бүрийнх панельд, нэгтгэл тайланд).
- Ханшийн бэлэн төлбөр (валютын бэлэн) ээлж нээхэд гараар өгсөн ханшаар — Монголбанкны ханш татахгүй
  (арилжааны бэлэн мөнгөний ханш нь албан ханш биш, §5b дүрэм).
- eBarimt: хотын татвар (НХАТ) хараахан дэмжигдээгүй (`totalCityTax` үргэлж 0) —
  зочид буудал/ресторан/барын харилцагчид шаардлагатай бол тусдаа change-control.
- eBarimt: зээлээр (credit) борлуулалт `B2C/B2B_INVOICE` төрлөөр илгээгдэж, зээлийн
  хэсэг `payments[].status = PAY` (бусад нь PAID) — `receiptTypeOf` (§8 T3). Нэхэмжлэх
  хожим төлөгдөхөд ТЕГ-ийн invoice → receipt урсгал хараахан хэрэгжээгүй; staging
  дээр ТЕГ-ийн хариуг тулгана.
- eBarimt: ТЕГ-ийн ангилалын кодын бүрэн лавлах татагддаггүй — хэрэглэгч кодоо
  гараар / Excel-ээр оруулна (код ЗОХИОХГҮЙ).
- eBarimt (developer портал 2026-08-тай тулгасан, `docs/integrations/01` §5): **ОАТ-ын
  тэмдэгтэй бараа** (архи, тамхи — `items[].data.stockQR[]`, 2025-04-01-ээс заавал) ба
  `type STOCK_QR` дэмжигдээгүй — ийм бараа зардаг харилцагчид eBarimt-ийг асаахаас өмнө
  тусдаа change-control; **`receipts[].data.location`** (GPS / LICENSE, 2026-06-18)
  илгээгдэхгүй (сонголтоор); **`reportMonth`** (өмнөх сарын B2B баримтыг сарын 1–7-нд
  нөхөн үүсгэх) UI байхгүй — `failed` баримтыг сарын дотор л [Дахин илгээх]-ээр;
  НӨАТ төлөгч бус байгууллагад баримт огт үүсгэхгүй (`NOT_VAT`-ийн албан утга «хилийн
  гадна борлуулсан» — НӨАТ төлөгч бус ч баримт олгох үүрэгтэй эсэхийг ITC-ээс тодруулна);
  бүтэн буцаалтын DELETE зөвхөн B2C_RECEIPT-д албан ёсоор — B2B-ийн зөв замыг staging тестээр.
  Мерчант ТЕГ-д НХАТ төлөгч / чөлөөлөгдөх төслөөр бүртгэлтэй бол тохиргооны таб + `get_ebarimt_status`
  анхааруулна; худалдан авагч чөлөөлөгдөх төсөл бол касс анхааруулна (автоматаар VAT_FREE/304 болгохгүй).
- QPay: нэг борлуулалтад QPay мөр НЭГ л байна (хоёр QR нэг сагсанд ҮГҮЙ); QPay
  буцаалт байхгүй; webhook `NEXT_PUBLIC_APP_URL` нийтэд хүрэхгүй бол зөвхөн гар
  [Шалгах]-аар төлөгдсөнийг мэднэ (readiness анхааруулна). eBarimt `payments[].code`
  QPay-д `BANK_TRANSFER_QPAY` (албан жагсаалт, 2026-09-25) — seed оноодог, хэлбэрийн `ebarimtCode`-оор засаж болно.

## Deploy

QPay (Фаз 3b): preDeploy `pos_settings.qpay_*` (6 багана), `pos_payment_methods.provider`,
`pos_qpay_intents` хүснэгт + 2 индекс нэмнэ (идемпотент). Env: `NEXT_PUBLIC_APP_URL`
(webhook-ийн нийтийн URL) — байхгүй бол QPay идэвхжихгүй (readiness problem).

`db:push --force` шинэ хүснэгт/баганыг үүсгэнэ; `inventory_items.sales_price` main-д
аль хэдийн байгаа (`scripts/apply-pending-ddl.mjs`). Шинэ данс (51900001, 31600003,
31600004, 51800002, 87000006, 87000007) `standard-accounts.ts`-д — "Стандарт данс нэмэх"-ээр орно.
