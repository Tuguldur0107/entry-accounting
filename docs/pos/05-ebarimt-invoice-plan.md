## 1. Зорилго

Борлуулалт eBarimt-д хоёр төрлөөр бүртгэгдэнэ:

| | Төлбөрийн баримт | Нэхэмжлэх |
|---|---|---|
| eBarimt төрөл | `B2C_RECEIPT` / `B2B_RECEIPT` | `B2C_INVOICE` / `B2B_INVOICE` |
| Утга | Төлбөр ТЭР ДОРОО төлөгдсөн | Дараа төлөгдөнө — мөнгө ороход ТӨЛӨЛТ хийнэ |
| Entry-д одоо | POS (бэлэн/карт/QPay/шилжүүлэг) — ✅ ажиллаж байна | POS-ийн «Зээлээр» хэлбэр л (`INVOICE` код, `PAY` төлөв — баталгаагүй); АР модулийн нэхэмжлэх eBarimt руу ОГТ явдаггүй; төлөлт ТЕГ-д мэдэгддэггүй |

Зорилго: **АР нэхэмжлэх → eBarimt нэхэмжлэх → төлөлт бүр → eBarimt**, ТЕГ-ийн
бүртгэл ба Entry-ийн авлага ҮРГЭЛЖ таарна.

## 2. Албан гарын авлага (POS API 3.0.pdf, 19 хуудас) — юу бичсэн, юу бичээгүй

2026-09-27-нд бүтэн уншив (Drive «POS API 3.0.pdf»). **«Нэхэмжлэх» зөвхөн `type`-ийн
хоёр утгын тайлбарт л гардаг.**

| Асуулт | Гарын авлагад |
|---|---|
| `B2C_INVOICE` / `B2B_INVOICE` | ✅ «…бүтээгдэхүүн, үйлчилгээний нэхэмжлэх» (нэг мөр) |
| Хэзээ INVOICE, хэзээ RECEIPT | ❌ бичээгүй |
| Нэхэмжлэхийн төлөлтийг илгээх зам / талбар | ❌ бичээгүй (`invoiceId`, `parentId` г.м. талбар БАЙХГҮЙ) |
| `payments[].status` утгууд (`PAID`, `PAY` …) | ❌ огт байхгүй. «status» гарчигтай жагсаалтад CASH, PAYMENT_CARD, BONUS_CARD_TEST л (кодын жагсаалт шиг — гарчгийн алдаа байж магадгүй) |
| Төлөгдөөгүй хэсгийн төлбөрийн код | ❌ байхгүй (`INVOICE` код алга) |
| Нэхэмжлэхэд / төлөлтөд сугалаа | ❌ бичээгүй — сугалаа зөвхөн худалдан авагчийн төрөл (иргэн тийм, ААН үгүй) ба taxType-аас |
| Баримт холбох талбар | `inactiveId` — ЗӨВХӨН засвар ба хэсэгчилсэн буцаалтад («засварлагдсан баримтад сугалаа ахин олгохгүй») |
| Хэсэгчилсэн төлөлт, худалдан авагч батлах, хугацаа | ❌ бичээгүй (`reportMonth` = «Баримт харьяалагдах тайлант сар» л) |
| DELETE `/rest/receipt` | `{id, date}` — нэхэмжлэхэд тусгай дүрэм бичээгүй |

**Бусад эх сурвалжаас мэдэгдэж буй:**
- `PAID` төлөв, `BANK_TRANSFER` / `BANK_TRANSFER_QPAY` код — хөгжүүлэгчийн порталын
  хуулбар + нээлттэй SDK (`docs/integrations/00` §7). Production-д `PAID`-тай баримт
  ДДТД авч байгаа (Хос Хас, 2026-09-27) → практикт хүчинтэй.
- TPI `getSalesTotalData` 2025-09-01-ээс **`prParentRno` — «нэхэмжлэхийн төлөлт болох
  баримт»** → ТЕГ-д төлөлтийг эх нэхэмжлэхтэй холбох механизм БИЙ, гэхдээ PosAPI-д
  ямар талбараар дамжуулах нь тодорхойгүй.
- DELETE зөвхөн иргэний баталгаажуулаагүй `B2C_RECEIPT`-д (`docs/integrations/01` P1-3).

## 4. Шат 0 — хариу авах (~1 өдөр, Монголын сүлжээнээс)

Гурван зам, зэрэг:

1. **Staging туршилт** — хамгийн найдвартай. Орчны бэлтгэл
   `docs/integrations/01-ebarimt-posapi-verification.md` §4 (staging PosAPI `.deb`,
   тест мерчант). Дараа нь:
   ```bash
   cd docs/pos/ebarimt-invoice-staging
   STAGING=yes POSAPI=http://localhost:7080 MERCHANT_TIN=<тест мерчант> \
     BUYER_TIN=<тест ААН-ийн ТТД> POS_NO=<posNo> DISTRICT=2301 ./run.sh
   ```
   `run.sh` (Entry-ийн `buildEbarimtReceipt`-ийн гаралттай ижил бүтэцтэй
   `invoice-b2b.json`-оос) дараах хувилбаруудыг ӨӨР ӨӨР нэхэмжлэх дээр илгээнэ:

   | Тест | Хариулах асуулт |
   |---|---|
   | T1a–d: `B2B_INVOICE` — код `INVOICE`/`BANK_TRANSFER`/`CASH` + `PAY`, payments-гүй | Q2 |
   | T2: `B2C_INVOICE` | Q4 (сугалаа ирсэн эсэх — утгыг ХАДГАЛАХГҮЙ) |
   | T3a: `inactiveId` + `B2B_RECEIPT` + `PAID` | Q1 |
   | T3b: `inactiveId` + `B2B_INVOICE` + `PAID` | Q1 |
   | T4: `inactiveId` + 440k `PAID` / 660k `PAY` | Q3 |
   | T5: нэхэмжлэхийг DELETE | Q5 |
   | T6: `inactiveId` + `reportMonth` өмнөх сар | Q6 |

   Скрипт `STAGING=yes`-гүй ажиллахгүй; хариунаас `lottery` / `qrData`-г хасаж
   `results/`-д хадгална (гарын авлага §5 хадгалахыг хориглодог).

   **Гар шалгалт (§4.3):** `stg-invoice.ebarimt.mn`-д мерчант ба худалдан авагчаар
   нэвтэрч T1/T3/T4 нэхэмжлэх ямар төлөвтэй (төлөгдсөн/хэсэгчлэн/нээлттэй),
   эх ↔ төлөлтийн холбоос (`prParentRno`) харагдах эсэх, худалдан авагч батлах
   товч байгаа эсэх (Q7)-ийг дэлгэцийн зургаар тэмдэглэнэ.

2. **developer.itc.gov.mn** — eBarimt PosAPI хуудсуудыг (нэхэмжлэх, payments,
   `prParentRno`) Монголын сүлжээнээс export хийж `docs/integrations/`-д хадгалах
   (гадаад IP-д нээгддэггүй — `00` §7).
3. **ITC-д албан асуулт** (posapi@itc.gov.mn) — §3-ийн Q1–Q8 (§8 загвар).

Хариу бүрийг энэ баримтын §3-т «✅ ХАРИУ: …, эх сурвалж» гэж бичнэ.

### Шат 1 — өгөгдлийн суурь (1 PR)
- `ar_ap_documents`: `ebarimtId`, `ebarimtStatus`, `ebarimtType`, `ebarimtDate`,
  `ebarimtReportedPaid` (ТЕГ-д мэдэгдсэн төлөлтийн нийлбэр). Багана НЭМЭХ л (хасахгүй).
- Илгээлтийн дарааллыг ерөнхий болгох: `pos_ebarimt_submissions`-д `source`
  (`pos_sale` | `arap_invoice` | `arap_payment`) + nullable эх ID; одоогийн POS мөр
  хөндөгдөхгүй. Backoff, `failed`, «Дахин илгээх», `pos.ebarimt_failed` мэдэгдэл
  НЭГ механизм.
- **Нээлттэй шийдвэр (product owner):** АР мөр ихэвчлэн үйлчилгээ (барааны
  картгүй) → ангиллын код хаанаас. Санал: **орлогын данс бүрт анхдагч ангиллын
  код** (тохиргоо), мөрөнд дарж болно. Код дутвал `[EBARIMT_UNMAPPED_ITEM]` — ЗОХИОХГҮЙ.

### Шат 2 — АР нэхэмжлэх → eBarimt нэхэмжлэх (1 PR)
- `postArApDocument` (ar_invoice) commit-ийн ДАРАА дараалалд → ТТД-тэй бол
  `B2B_INVOICE`, эс бөгөөс `B2C_INVOICE`. Батлалт eBarimt-ээс болж ХЭЗЭЭ Ч зогсохгүй.
- POS «Зээлээр» ижил загвар (Q2-оор кодыг засна).
- Төрлийн шийдвэр ЗӨВХӨН `lib/arap/document-kind.ts` (CLAUDE.md §5d).

### Шат 3 — төлөлт → eBarimt (1–2 PR)
- Авлагын төлөлт 6 газраас үүсдэг (касс `lib/actions/cash.ts`, банкны хуулга
  `lib/cash/import-statement.ts`, POS, харилцан суутгал `settleArApOffset`, ECL,
  кредит нэхэмжлэл). Газар бүрд hook нэмбэл орхигдоно → **СКАННЕР**: `ebarimtStatus =
  sent` нэхэмжлэх бүрийн `Σ settlements (төлөлт төрлийн) − ebarimtReportedPaid > 0`
  бол Q1/Q3-ийн хариугаар төлөлтийн баримт илгээнэ. Тикер нь одоогийн eBarimt
  worker. Нэг ч төлөлт чимээгүй үлдэхгүй.
- Төлөлтөд ТООЦОХГҮЙ: ECL хасалт, кредит нэхэмжлэл (Q5 — засвар). Харилцан суутгал — Q8.
- Буцаагдсан төлөлт (касс/хуулгын буцаалт) → Q5-ийн хариугаар засвар.

### Шат 4 — ТЕГ ↔ Entry тулгалт (nginx прокси + TPI түлхүүрийн дараа)
- `getSalesTotalData` (status 3 = нэхэмжлэх, `prParentRno`) ↔ АР, `reconcileDdtd`
  (`lib/itc/tpi.ts`) дээр. «ТЕГ-д нээлттэй / Entry-д төлөгдсөн» г.м. зөрүү
  `reconcile_modules`-ийн «ТЕГ ↔ Entry» хэсэгт.

### UI / модулиуд
- **Авлага:** жагсаалтад eBarimt төлөвийн багана + chip шүүлт (`lib/status.ts`),

- **НӨАТ:** НӨАТ төлөгчид гаралтын НӨАТ ↔ eBarimt тулгалт (Q6-ийн хариугаар сар).

- **AI / MCP:** `get_ebarimt_status`-д АР нэхэмжлэх, `resend_ebarimt` АР-д.

## 8. ITC-д илгээх асуулт (загвар)

> Сайн байна уу. Бид PosAPI 3.0-оор (оператор: Хос хас технологи, posNo 10000878)
> нягтлан бодох бүртгэлийн системээс нэхэмжлэх (`B2B_INVOICE` / `B2C_INVOICE`)
> гаргах гэж байна. «POS API 3.0» гарын авлагад нэхэмжлэхийн төлөлтийн урсгал
> тусгагдаагүй тул дараах асуултад хариулж, холбогдох баримт бичгийг илгээнэ үү:
> 1. Нэхэмжлэх төлөгдөхөд PosAPI-д юу илгээх вэ (жишээ нь `inactiveId`-тай дахин
>    илгээх үү; RECEIPT эсвэл INVOICE төрлөөр)? TPI-ийн `prParentRno` хэрхэн бүрддэг вэ?
> 2. Төлөгдөөгүй дүнгийн `payments[].code` ба `status` ямар утгатай байх вэ?
> 3. Нэхэмжлэхийг хэсэгчлэн (хэд хэдэн удаа) төлөхөд юу илгээх вэ?
> 4. `B2C_INVOICE` ба түүний төлөлтөд сугалаа олгогдох уу?
> 5. Нэхэмжлэхийг цуцлах / буцаах (кредит нэхэмжлэл) зөв арга?
> 6. Төлөлтийн баримт аль тайлант сард хамаарах вэ (`reportMonth`)?
> 7. B2B нэхэмжлэхийг худалдан авагч баталгаажуулах шаардлагатай юу, хугацаатай юу?
> 8. Харилцан суутган тооцоогоор хаагдсан авлагыг төлөлт гэж илгээх үү?
