## 1. Байгууллага устгах — `ON DELETE RESTRICT` гацаа

**Асуудал (тестээр батлагдсан).** Схемд 46 FK `ON DELETE RESTRICT` байна.
Postgres RESTRICT-ийг cascade устгалтын ДУНД шууд шалгадаг. Иймээс
`organizations` мөрийг устгахад дараах байгууллагууд гацна:

- цалин бодсон (`payroll_run_lines → employees`);
- POS борлуулалттай (`pos_sales → ar_ap_documents`, `pos_shifts → cash_accounts`);
- АР/АП төлбөр холбосон (`ar_ap_settlements → ar_ap_documents`);
- хангамж, өртөг, ҮХ-ийн элэгдэлтэй.

Нөлөөлөх замууд: Тохиргоо → «Байгууллага устгах», MCP `delete_company`,
демо сэргээх (`lib/actions/demo.ts`). Тестүүд үүнийг гараар дараалуулан устгаж
тойрч байсан (`tests/procurement-flow.test.ts` `purgeOrg`,
`simulation-regressions` цэвэрлэгээ).

**Санал.** Схемийн 46 FK-г `onDelete: "no action"` болгоно. NO ACTION нь
шалгалтыг statement-ийн ТӨГСГӨЛД хийдэг. Үр дүнд нь:

- cascade устгалт давна;
- ганц мөр устгах хамгаалалт (баримттай харилцагч, хөдөлгөөнтэй бараа г.м.)
  ЯГ хэвээр үлдэнэ;
- схемд RESTRICT дахин орохоос статик тест хамгаална.

Тестүүдийн гар дараалалтай цэвэрлэгээг жинхэнэ `deleteOrganizationForUser`
замаар солино. Давтан үүсгэх тестийн patch бэлэн.

**Эрсдэл.** preDeploy-ийн `drizzle-kit push` production-д 46 constraint-ийг
DROP + ADD хийнэ (NOT VALID биш тул хүснэгт бүрийг validate хийж, богино
хугацаанд түгжинэ). Pilot хэмжээнд секундын асуудал. Push нь «rename?»
асуулт тавихгүй (FK-ийн өөрчлөлт), гэхдээ эхлээд staging/хуулбар DB дээр
турших нь зөв.

- **D-DEL-1:** Схемийн өөрчлөлтийг зөвшөөрөх үү? Deploy-ийн өмнө Railway
  нөөцлөлтийг (backup) шалгана.

## 3. ENT-029 — Кредит нэхэмжлэл / худалдан авагчийн буцаалт (B2B)

**Асуудал.** АР/АП-д сөрөг баримт байхгүй. `create_arap_invoice` сөрөг мөрийг
хүлээн авдаггүй бөгөөд буцаалт одоогоор зөвхөн POS-д (`return_pos_sale`)
байна. B2B буцаалтад гурван зүйл нэг баримтаар холбогдох ёстой:

- авлага бууруулах;
- НӨАТ-ын гаралтыг бууруулах;
- бараа буцаах (`return_in`).

**Санал.** Шинэ `documentType`: `ar_credit_note` / `ap_debit_note`. Эх
нэхэмжлэл (`sourceDocumentId`) заавал байна. Мөр бүр эх мөртэйгээ холбогдож,
буцаах тоо нь эх мөрийн үлдэгдлээс хэтрэхгүй.

```
АР кредит нэхэмжлэл:  Dr 51900001 Борлуулалтын буцаалт/хөнгөлөлт (эсвэл 51100000)
                      Dr 31410000 НӨАТ өглөг (эх баримт НӨАТ-тай бол)
                      Cr 13110000 Авлага
Бараатай бол:         return_in хөдөлгөөн → сар хаалтад дунджаар үнэлэгдэнэ
                      (POS-ийн буцаалттай ИЖИЛ — docs/cost README «үнэгүй орлого»)
Суутгал:               эх нэхэмжлэлийн үлдэгдлээс хасна (ar_ap_settlements), илүүдэл → урьдчилгаа
```

НӨАТ-ын тайланд `computeVatReturn` гаралтыг Cr − Dr гэж бодож байгаа тул
өөрчлөлт шаардахгүй. eBarimt-д холбогдох бол `inactiveId` гинжийн дүрмийг
(§5c) дагана.

**Шийдвэр (2026-09-24, зөвлөмжөөр батлагдсан — хэрэгжилт CLAUDE.md §5d):**
D-CN-1 → `51900001` (АР-ын орлогын мөр; сегмент эх мөрийнх). D-CN-2 → эх
нэхэмжлэх ЗААВАЛ. D-CN-3 → батлахад эх нэхэмжлэхэд автоматаар тооцно,
илүүдэл = харилцагчийн кредит (кассаар буцаан олгох эсвэл дараагийн
нэхэмжлэхтэй суутгах). D-CN-4 → eBarimt дараагийн фаз. Нэмэлт: кредит нь эх
нэхэмжлэхийн ханшаар; PO-той нэхэмжлэхийн дебит нэхэмжлэх ENT-064-тэй хамт.

**Анхны асуултууд:**

- **D-CN-1:** Буцаалтын данс нь `51900001` «Борлуулалтын хөнгөлөлт (contra)»
  юу, эсвэл тусдаа «Борлуулалтын буцаалт» данс нэмэх үү? (IS-д орлогын
  хасалт болж харагдана.)
- **D-CN-2:** Эх нэхэмжлэл заавал уу, эсвэл «эх баримтгүй хөнгөлөлтийн кредит»
  зөвшөөрөх үү?
- **D-CN-3:** Эх нэхэмжлэл аль хэдийн бүрэн төлөгдсөн бол илүүдлийг харилцагчийн
  урьдчилгаа болгох уу, эсвэл кассаар буцаан олгох уу?
- **D-CN-4:** eBarimt-тай холбох нь энэ фазад уу (B2B баримтыг `inactiveId`-аар
  засах), эсвэл дараагийн фазад уу?

## 4. ENT-065 — Найдваргүй авлага хасах, ECL нөөц (IFRS 9)

**Асуудал.** Write-off / ECL функц байхгүй. Симуляцид хэрэглэгч авлагыг гар
журналаар (Dr 87000002 / Cr 13110000) хаасан. Үр дүнд нь:

- нэхэмжлэл нээлттэй хэвээр насжилтад үлдсэн;
- `reconcile_modules` зөрүү илрүүлсэн ч сар хаалт хориглогдоогүй.

**Санал.**

- `write_off_arap_document`: нэхэмжлэлийг «хассан» төлөвт оруулна
  (`ar_ap_settlements`-д write-off төрлөөр). GL: Dr ECL нөөц (эсвэл зардал) /
  Cr Авлага. Батлах эрх `ar:post` + AI хязгаар.
- ECL нөөцийн сарын delta (хялбаршуулсан арга, насжилтын provision matrix —
  `ifrs-9-financial-instruments.md`):
  **нөөц = Σ(насжилтын бүлгийн үлдэгдэл × хувь) − одоогийн нөөцийн үлдэгдэл**.
  Үр дүн нь НООРОГ журнал (§9).
- Хяналтын данс (`13110000`, `31000001`) руу ГАР журнал батлахад анхааруулга.
- `get_month_end_checklist`: `reconcile_modules`-ийн АР/АП/касс зөрүү ≠ 0 бол
  «хаахад бэлэн биш».

**Нээлттэй шийдвэр:**

- **D-ECL-1 — дансны зөрчил.** Knowledge-ийн IFRS 9 файл нөөцийг `12000001`,
  зардлыг `87000002` гэж заасан. Гэтэл стандарт жагсаалтад:
  - `12000001` = «Дансны авлага»;
  - `12000099` = «Авлагын ECL нөөц»;
  - `87000002` = «Үнэ цэнийн бууралтын алдагдал (IAS 36)».

  Санал: нөөц `12000099`, зардал нь тусдаа «Авлагын үнэ цэнийн бууралт (IFRS 9)»
  данс. Хоёуланг нь `arap_settings`-ийн роль болгоно, кодод хатуу бичихгүй.
- **D-ECL-2:** Provision matrix-ийн хувь (1/5/10/25/50/100%) байгууллага
  тохируулдаг уу, эсвэл жишгээр түгжих үү?
- **D-ECL-3:** Татварын талд найдваргүй авлага хасагдах зардал биш байж
  болно (ААНОАТ-ын хуулийн нөхцөл) → IAS 12 түр зөрүү. Энэ фазад мэмо
  тэмдэглэлээр л хязгаарлах уу?
- **D-ECL-4:** Хасалт хийсний дараа мөнгө орж ирвэл (recovery) — орлого уу,
  эсвэл нөөцийг сэргээх үү?

## 7. Хуучин өгөгдлийн залруулга (аудит M3–M7)

PR #79-ийн засварууд цаашид зөв ажиллана. Харин өмнө бичигдсэн өгөгдлийг
чимээгүй өөрчлөөгүй. Ямар залруулга хийх нь шийдвэр:

- **D-HIST-1 (M3, ENT-023):** Урьд хэт их бичигдсэн FX олзын дараа дараагийн
  тэгшитгэл их хэмжээний ГАРЗ **батлагдсан** хэлбэрээр бичнэ. Санал:
  - carrying ба өмнөх тэгшитгэлийн зөрүү материаллаг бол журналыг НООРОГ
    болгох;
  - `adjustment_type: prior_period` + «өмнөх үеийн залруулга» гэж тэмдэглэх.
- **D-HIST-2 (M4, ENT-024/052):** Хаагдсан саруудын НӨАТ тайлан шинэ дүрмээр
  өөр тоо харуулна. Илгээсэн тайлантай зөрүүг харуулах «илгээсэн дүн» талбар
  хадгалах уу, эсвэл зөвхөн мэдэгдэл үү?
- **D-HIST-3 (M5, ENT-002):** Түүх дутуу хуучин ҮХ-ийн картууд эрт зогсох эсвэл
  нэг сард үлдэгдлээ бүхэлд нь элэгдүүлэх эрсдэлтэй. Санал: илрүүлэх
  жагсаалт + «нээлтийн хуримтлагдсан элэгдэл» оруулах залруулгын урсгал
  (одоо карт идэвхтэй бол боломжгүй).
- **D-HIST-4 (M6, ENT-022):** POS-ийн зарлагын төрөл тогтмол зардлын данс руу
  бичиж байсан байгууллагууд. Анхааруулга аль хэдийн нэмэгдсэн
  (`get_pos_status`). Өмнөх COGS бичилтийг залруулгын НООРОГ журналаар засах
  уу?
