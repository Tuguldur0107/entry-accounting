# Банкны гүйлгээ (Фаз 2, Голомт CGWTXNADD) — аюулгүй байдлын шийдвэрийн санал

**Төлөв:** D1–D7 БАТЛАГДСАН (product owner 2026-10-02). Кодлолт банкны хариуг
хүлээж байна — §8 Q1 (Хавсралт 3: стандарт TOTP эсэх) ба Q2 (нэг код олон
гүйлгээнд). Хариу ирэхээс өмнө Entry-д гүйлгээний код БИЧИГДЭХГҮЙ; эхний алхам
P0 (UAT, тусдаа скрипт). D1-A-аар X-Golomt-Key Entry-д ХЭЗЭЭ Ч орохгүй — зөвхөн
6 оронтой код батлах мөчид санах ойд (`CLAUDE.md` §5f).

Холбоотой: `docs/dev/bank-api.md` (Фаз 1, протокол), `CLAUDE.md` §5f, §9.
Эх баримт: Голомт OBI SPEC 1.5.9 (repo-д БАЙХГҮЙ), банкны албан хариу (2026-10).

## 1. Юу өөрчлөгдсөн бэ (банкны албан хариу, 2026-10)

- Entry-д нээгдсэн 6 сервис: LGIN, ACCTBALINQ, OPERACCTDET, OPERACCTSTA, ACCCHK
  (Голомтын болон Голомтын бус данс), **CGWTXNADD** (байгууллага өөрийн данснаас
  гүйлгээ).
- OBI нь Public API — IP хаяг, нэмэлт сертификат шаардахгүй. Монголын relay
  ХЭРЭГГҮЙ.
- Гүйлгээг тоон гарын үсгээр биш, **X-Golomt-Key** (16 оронтой нууц)-ээс
  үүсгэсэн цагт суурилсан кодоор (header `X-Golomt-Code`, SPEC Хавсралт 3)
  баталгаажуулна.
- CGWTXNADD: `POST /v1/transaction/cgw/transfer`; талбар `registerNumber`,
  `remarks`, `type` (TSF / PMT / PRC), `refCode` …; зөвхөн банкинд зөвшөөрөгдсөн
  эх данснаас.

## 2. Аюулын загвар — яагаад энэ нь Фаз 1-ээс өөр вэ

Фаз 1-д Entry-д байгаа нууц (нэвтрэх нэр, нууц үг, session/IV key) алдагдвал
хуулга, үлдэгдэл ХАРАГДАНА — мөнгө ХӨДЛӨХГҮЙ. Фаз 2-т **нэвтрэх мэдээлэл +
X-Golomt-Key** хоёулаа нэг газар байвал тэр газар = байгууллагын данснаас
мөнгө гаргах бүрэн эрх.

| Аюул | Жишээ | Хамгаалалт |
|------|-------|------------|
| DB + `AUTH_SECRET` алдагдах | Railway-ийн нууц, нөөц файл задрах | D1: түлхүүр серверт ҮГҮЙ (A) эсвэл серверийн түлхүүрээр тайлагдахгүй (C) |
| Хэрэглэгчийн бүртгэл булаагдах | Нууц үг fishing | D2 maker/checker, батлахад дахин нэвтрэх, D3 хязгаар, D4 хүлээн авагчийн хүлээлт |
| Дотоод хүн (Entry баг) | Дэмжлэгийн хандалт | Дэмжлэгийн сесс, platform admin гүйлгээ ҮҮСГЭХ / БАТЛАХ ЭРХГҮЙ |
| AI / prompt injection | Нэхэмжлэхийн текстэд «шилжүүл» | D5: AI зөвхөн ноорог (бүртгэлтэй данс, хязгаартай); хүн линкийн хуудсанд дүн + хүлээн авагчийг ХАРЖ кодоор батална |
| Хуурамч батлах линк | AI-ийн хариунд `entry.mn`-ээс өөр домэйн | Хулгайлсан код 30 сек хүчинтэй бөгөөд Голомтын нэвтрэх мэдээлэл + session/IV key-гүй ашиглагдахгүй; MCP URL elicitation дэмждэг клиентэд линк моделиор дамжихгүй (§4a) |
| Хүлээн авагчийн данс солих луйвар (BEC) | «Манай данс өөрчлөгдсөн» и-мэйл | D4: шинэ дансанд ACCCHK + хүлээлт + эзэнд мэдэгдэл |
| Давхар төлбөр | Timeout-ийн дараа дахин илгээх | D6 |
| Fork / dedicated сервис | Харилцагч өөрөө host хийх | Анхнаасаа УНТРААЛТТАЙ, env-ээр л нээгдэнэ |

## 3. D1 — X-Golomt-Key хадгалах арга

| Хувилбар | Тайлбар | DB + AUTH_SECRET алдагдвал | UX | Тэмдэглэл |
|----------|---------|----------------------------|-----|-----------|
| **A. Хадгалахгүй** | Түлхүүрийг батлагч(ид) өөрийн authenticator апп-д (Google Authenticator, 1Password …) оруулна. Батлах үед 6 оронтой кодыг Entry-д бичнэ → Entry `X-Golomt-Code` болгон илгээнэ | Мөнгө ХӨДЛӨХГҮЙ | Гүйлгээ бүрд код бичнэ (30 сек) | Хавсралт 3 нь RFC 6238 (HMAC-SHA1, 30 сек, 6 орон) байх НӨХЦӨЛТЭЙ. Багц гүйлгээ: нэг код хэд хэдэн хүсэлтэд хүчинтэй эсэхийг банкнаас асууна |
| **C. Батлагчийн нууц үгээр шифрлэх** | Түлхүүрийг батлагчийн тусдаа «гүйлгээний нууц үг»-өөр (Argon2id → AES-GCM) шифрлэж хадгална; сервер тэр нууц үгийг хадгалахгүй. Батлахад нууц үгээ оруулна → санах ойд л тайлагдаж кодыг сервер үүсгэнэ | Мөнгө хөдлөхгүй (нууц үгийг brute-force хийх шаардлагатай — урт нууц үг) | Батлахад нууц үг | Хавсралт 3 стандарт биш байсан ч ажиллана. Батлагч солигдвол түлхүүрийг шинээр оруулна |
| B. Серверийн түлхүүрээр шифрлэх | `encryptSecret` (AUTH_SECRET) эсвэл тусдаа `BANK_TXN_KEY` env | Мөнгө ХӨДӨЛНӨ | Хамгийн хялбар | Product owner-ийн 2026-10-01 анхны хүсэлт. Фаз 1-ийн «алдагдсан ч мөнгө хөдлөхгүй» баталгааг алдана. Тусдаа KMS / signer сервис нь startup-д үнэтэй |

**Санал: A**, Хавсралт 3 нь стандарт TOTP мөн бол. Үгүй бол **C**. B-г
сонговол дор хаяж тусдаа `BANK_TXN_KEY` (AUTH_SECRET биш), Railway-ийн
тусдаа service-д л байх, хязгаар (D3) хатуу байх нөхцөлтэй.

Бүх хувилбарт: түлхүүр / код ХЭЗЭЭ Ч client-д буцахгүй, лог, аудит, алдааны
текст, тестэд гарахгүй; талбар write-only; `X-Golomt-Code`-ийг логт бичихгүй.

## 4. D2 — Maker / checker

- **Үүсгэгч** (шинэ эрх `bank_pay:write`): төлбөрийн даалгавар НООРОГ үүсгэнэ.
- **Батлагч** (`bank_pay:post`): өөр хүн. Батлах мөчид:
  - сүүлийн 5 минутад нууц үгээр дахин нэвтэрсэн (step-up),
  - D1-ийн код / нууц үг,
  - төлөв нөхцөлтэй шилжилт (`WHERE status = 'pending_approval'`, C4 — `lib/state-guard.ts`).
- **Нэг хүний горим** (жижиг компани — нэг нягтлан): эзэн Тохиргооноос ИЛ асаана,
  аудиттай, эзэнд мэдэгдэлтэй; энэ горимд хязгаар (D3) тусдаа, бага. D1-A/C-ийн
  код нь өөрөө хоёр дахь хүчин зүйл болно.
- Дэмжлэгийн сесс, REST token, Console — үүсгэх ч, батлах ч ЭРХГҮЙ. MCP — зөвхөн
  ноорог (D5), батлах ЭРХГҮЙ.

## 4a. Батлах линк (product owner 2026-10-02)

AI-тай чатаар бэлдсэн гүйлгээг тэр чатаас гаралгүй, утсаар хоёр алхмаар батална:

```
Чат: «Батад түрээс шилжүүл»
  → AI → MCP create_bank_payment_draft (ноорог, бүртгэлтэй данс, хязгаар шалгана)
  → tool-ийн хариу: «Гүйлгээ батлах хүсэлт · https://entry.mn/pay/<token>» — ТЭР ЧАТАД
     (Telegram / и-мэйлээр БИШ; апп доторх хонхонд нөөц мэдэгдэл л)
  → хэрэглэгч линкийг утсаар нээнэ → кодоо оруулна → «Батлах»
  → AI → get_bank_payment_status → «Илгээгдсэн ✓»
```

**Хуудас — mobile, хамгийн бага:** дүн (том), хүлээн авагч (ACCCHK-ийн далдлагдсан
нэр + банк + данс), эх данс, утга — 3–4 мөр; 6 оронтой кодын талбар (тоон гар);
«Батлах», «Татгалзах». Өөр цэс, навигаци БАЙХГҮЙ. Гүйлгээний мэдээллийг харуулах нь
ЗААВАЛ — эс бөгөөс AI-ийн бэлдсэн юуг ч сохроор батлах болно (код гүйлгээнд
уягддаггүй, зөвхөн «хүн зөвшөөрсөн»-ийг баталдаг). Үр дүн: «Илгээгдсэн» / «Алдаа: …» /
«Шалгаж байна» (`unknown`, D6).

**Линкийн дүрэм:**
- Token нэг удаагийн, **15 минут**, тодорхой гүйлгээ + батлагчид уягдсан; DB-д sha256
  hash л. Хугацаа дуусвал ноорог үлдэнэ — AI дахин линк гаргаж болно.
- Entry-д нэвтэрсэн сесс шаардана (утсан дээр ихэвчлэн нээлттэй) — нууц үг дахин
  асуухгүй; сесс + authenticator код = 2 хүчин зүйл. Дэмжлэгийн сесс нээж чадахгүй.
- Батлах = нөхцөлтэй шилжилт `pending_approval → sending` (C4), хязгаар (D3)
  транзакц дотор түгжээтэй, `refCode` (D6) — давхар дарахад нэг л илгээгдэнэ.
- Код (`X-Golomt-Code`) санах ойд л — DB, лог, аудитад ОРОХГҮЙ.
- MCP клиент URL elicitation дэмждэг бол линкийг сервер клиентэд шууд нээлгэнэ
  (моделиор дамжихгүй); эс бөгөөс tool-ийн хариуны текстээр.
- Олон гүйлгээ (цалин): нэг хуудсанд нийлбэрээр, НЭГ кодоор батлах нь §8 Q2-ын
  хариунаас хамаарна.

## 5. D3 — Хязгаар

- `bank_payment_settings`: нэг гүйлгээний дээд дүн, өдрийн нийт (УБ цагаар),
  нэг хүний горимын дүн. `null` = ТОГТООГООГҮЙ → гүйлгээ ХААЛТТАЙ (Entry тоо
  зохиохгүй, `docs/billing` §null-ийн дүрэмтэй адил).
- Өсгөлт: зөвхөн эзэн, вэбээс, **24 цагийн дараа** хүчинтэй, мэдэгдэлтэй.
  Бууруулалт / унтраах: шууд.
- Хязгаарыг батлах мөчид транзакц дотор (тухайн өдрийн илгээгдсэн + илгээж
  буй) түгжээтэй шалгана — зэрэгцээ батлалт давж гарахгүй.
- Банкны талын хязгаарыг (Корпорэйт Гэйтвэй гэрээний) мөн тогтоолгохыг
  харилцагчид зөвлөнө — Entry-ийн хязгаар нь ДОТООД давхарга.

## 6. D4–D6 — Хүлээн авагч, AI, давхар төлбөр

**D4 Хүлээн авагч**
- Зөвхөн бүртгэлтэй харилцагч / ажилтны данс (чөлөөт текстээр данс бичихгүй).
- Шинэ эсвэл ӨӨРЧЛӨГДСӨН данс: ACCCHK-ээр шалгаж (далдлагдсан нэрийг хэрэглэгч
  харна), анхны төлбөр **24 цагийн** дараа; данс өөрчлөгдсөн бүрд эзэнд шууд
  мэдэгдэл.

**D5 AI** (2026-10-02-нд шинэчлэв) — `lib/ai/tools.ts`-д ЗӨВХӨН
`create_bank_payment_draft` (ноорог + батлах линк, `externalRef`-ээр idempotent,
`surfaces: ["mcp"]`) ба `get_bank_payment_status`. Батлах / илгээх tool БАЙХГҮЙ;
REST-д ч гаргахгүй. AI шинэ хүлээн авагчийн данс нэмж чадахгүй (D4). Ноорог нь
«Шууд бичих» горимд ч ноорог хэвээр (§9). `tests/`-д статик шалгалт: гүйлгээг
`sending` болгодог зам tool давхаргаас дуудагдахгүй.

**D6 Давхар төлбөр**
- `refCode` = Entry-ийн төлбөрийн ID (давтагдашгүй; банк ЗӨВХӨН `^[a-zA-Z0-9_]*$` — зураасгүй, UUID-ийн «-»-ийг хасна). Төлөв:
  `draft → pending_approval → sending → sent | failed | unknown`.
- Timeout / 5xx / хариу тайлагдахгүй → `unknown`. АВТОМАТААР ДАХИН ИЛГЭЭХГҮЙ.
  OPERACCTSTA-аар `refCode` / дүн / огноогоор тулгаж `sent` / `failed` болгоно;
  тулгагдахгүй бол «Анхаарах»-д ил (ХЭЗЭЭ Ч чимээгүй үлдэхгүй).
- GL: `sent` болсон төлбөр → кассын зарлагын баримт (ердийн замаар); хуулга
  импортлоход тэр гүйлгээг давхар бичихгүй (externalRef холбоос) — §8 Q6-ийн
  хариугаар нарийвчилна.

## 8. Банкнаас тодруулах асуулт

1. ~~**Хавсралт 3**~~ — **ХАРИУЛТ (2026-10-02, SPEC Хавсралт 3):** стандарт RFC 6238 TOTP — X-Golomt-Key = 16 тэмдэгт BASE32 нууц, HMAC-SHA1, 30 сек, 6 орон (`TimeBasedOneTimePasswordUtil`). Google Authenticator-т шууд нэмэгдэнэ → **D1-A хэрэгжих боломжтой**.
2. Нэг код хэд хэдэн гүйлгээнд хүчинтэй юу, эсвэл гүйлгээ бүрд шинэ код уу?
3. `refCode` давтагдвал банк татгалзах уу (idempotency)?
4. Гүйлгээний төлөв шалгах сервис бий юу (CGWTXNADD-ийн хариу ирээгүй үед)?
5. `type` TSF / PMT / PRC-ийн ялгаа; банк хоорондын шилжүүлэг (Хаан, ХХБ …)
   CGWTXNADD-аар боломжтой юу, хүлээн авагчийн банкны код ямар хэлбэртэй?
6. Хуулгад (OPERACCTSTA) `refCode` / `remarks` харагдах уу (тулгалт, D6)?

   `040000` / BIC), `accountId`-д IBAN уу, данс уу (UAT-д `vrfctn:false`).
