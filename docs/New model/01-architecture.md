# Даалгавар: entry системийг open-core + extension архитектур руу шилжүүлэх төлөвлөгөө

Чи одоо код ЗАСАХГҮЙ. Зөвхөн codebase-ийг нарийн судалж, PLAN.md файл боловсруулна. Төлөвлөгөөг би баталсны дараа л хэрэгжүүлэлт эхэлнэ.

## Контекст
entry бол FastAPI + React 19 + PostgreSQL дээр бичигдсэн, Railway дээр deploy хийгдсэн multi-tenant нягтлан бодох SaaS. SmartGPS гэдэг production хэрэглэгч аль хэдийн нэвтэрч, бодит өгөгдөл оруулж эхэлсэн. Систем 111 tool-той MCP server-тэй.

Стратегийн зорилго:
1. Эхний ээлжинд SaaS хэлбэрээр жижиг бизнесүүдэд худалдаалах
2. Хэрэглэгчид цөмийн кодыг засахгүйгээр, MCP/API дээр extension бичиж (vibe coding-оор) өөрсдөө customize хийх боломжтой болгох
3. 12+ сарын дараа core/ хэсгийг public mirror-оор нээж (AGPL), integration болон enterprise хэсгийг хаалттай үлдээх open-core загварт шилжих боломжтой байх
4. Төрийн системүүд (ebarimt эхний ээлжинд; etax, e-balance, portal.ndaatgal-д upload-ready файл экспорт) холбох суурийг бэлдэх

## 1-р үе шат: Судалгаа (заавал эхэлж хий)
Дараах асуултуудад codebase-ээс бодит баримттайгаар (файлын зам, мөр) хариул:

**а) Модулийн бүтэц ба хамаарал**
- Ямар модулиуд байна (GL, АР/АП, касс, бараа, PO, үндсэн хөрөнгө, цалин, НӨАТ, ханш, үе хаалт, аудит)?
- Модулиуд хоорондоо хэрхэн харьцдаг вэ: service/function дуудлагаар уу, эсвэл бусад модулийн хүснэгт рүү шууд ORM/SQL хандалтаар уу? Шууд хандаж буй бүх газрыг жагсаа.
- Хамаарлын граф зур. Циклик хамаарал байгаа эсэх?

**б) Нууц мэдээлэл**
- Код, config, git түүх, миграци, test, seed data дотор hardcoded API key, нууц үг, token, гэрчилгээ байгаа эсэхийг шалга (git log -p, .env файлууд, docker/railway тохиргоо орно).
- Tenant тус бүрийн гадаад credential хаана, ямар хэлбэрээр хадгалагдаж байна?

**в) Integration-ууд**
- Гадаад системтэй холбогдож буй код (QPay, SocialPay, Монголбанкны ханш, и-мэйл, бусад) хаана байна, цөмийн логиктой хэр сүлжилдсэн бэ?
- Event/hook/signal механизм байгаа эсэх (жишээ нь "нэхэмжлэх батлагдлаа" гэдгийг сонсох боломж)?

**г) Цөмийн дүрмийн хамгаалалт**
- Дараах дүрмүүд одоо ХААНА шалгагдаж байна: application code-д уу, DB constraint/trigger-т үү, эсвэл огт байхгүй юу?
  - Журнал бүрт дебет = кредит
  - Хаагдсан тайлант үе рүү бичилт хийхгүй
  - Батлагдсан баримтыг засахгүй/устгахгүй, зөвхөн буцаалт хийнэ
  - Tenant isolation (нэг tenant нөгөөгийн өгөгдлийг харахгүй)
  - Дансны модны бүлгийн дүрэм
- Application code-оор л хамгаалагдсан бол extension эсвэл шууд DB хандалт эдгээрийг тойрч чадах эсэх?

**д) MCP/API давхарга**
- 111 tool нь service давхаргыг дуудаж байна уу, эсвэл DB-д шууд хандаж байна уу?
- Public API (REST) ба MCP tool-ууд давхардсан логиктой юу?
- Versioning, auth, rate limit, tenant scoping хэрхэн хийгдсэн?

**е) Өгөгдөл ба миграци**
- Миграцийн хэрэгсэл (Alembic?) ямар төлөвтэй, бүх миграци reversible юу?
- SmartGPS-ийн өгөгдөл ямар хүснэгтүүдэд, хэр хэмжээтэй байна (мөрийн тоо)?
- Backup/restore одоо хэрхэн хийгддэг вэ (Railway volume, pg_dump)?
- Test coverage ямар түвшинд, нягтлан бодох логикийн тест байгаа юу?

Судалгааны дүнг PLAN.md-ийн "Одоогийн байдал" хэсэгт бич. Таамаглаж бичихгүй, олдоогүй бол "олдсонгүй" гэж бич.

## 2-р үе шат: Зорилтот архитектур
Судалгаанд үндэслэн дараахыг санал болго:

1. **Хавтасны бүтэц**: core/ (нээж болох хэсэг) ба integrations/, enterprise/ (хаалттай) гэсэн хуваарилалт. Хамаарлын чиглэл: integrations → core зөвшөөрнө, core → integrations ХОРИГЛОНО. Үүнийг import-linter эсвэл ижил хэрэгслээр CI-д шалгах.
2. **Цөмийн дүрмийг DB constraint/trigger + core service давхарга руу шилжүүлэх.** Дүрэм бүрийг хаана хамгаалахыг заа.
3. **Нууц мэдээллийг env variable болон tenant тус бүрийн шифрлэсэн credential хүснэгт рүү шилжүүлэх.** Git түүхэнд нууц олдсон бол цэвэрлэх төлөвлөгөө.
4. **Domain event механизм** (жишээ нь document.posted, period.closed) — integration-ууд цөмийг өөрчлөхгүйгээр сонсдог байх. Queue, retry, idempotency key, offline fallback тооц.
5. **Integration adapter interface**: ebarimt-ийг эхний adapter болгож загварчил; etax/e-balance/ndaatgal-д тайлангийн экспорт (upload-ready файл) хэлбэрээр эхлэх.
6. **Extension SDK**: хэрэглэгч MCP/API дээр extension бичих загвар. Extension-ий хийж болох/болохгүй зүйлийн хил (permission scope). Sandbox tenant. Extension template repo-ийн бүтэц.
7. **AGENTS.md / CLAUDE.md**: extension бичих AI-д зориулсан заавар (архитектур, зөвшөөрөгдсөн tool, хориглосон үйлдэл, тестийн шаардлага).
8. **Public mirror-д бэлтгэл**: core/-г тусад нь package болгон build хийх боломж, лицензийн файл, CI-д mirror sync (одоо асаахгүй).

## 3-р үе шат: SmartGPS-ийн өгөгдлийг алдалгүй шилжүүлэх (ХАМГИЙН ЧУХАЛ)
Энэ бол production өгөгдөл. Дараах шаардлагыг ЗААВАЛ тусга:

- Бүх миграци backward-compatible, **expand → migrate → contract** загвараар хийгдэнэ. Хүснэгт, багана шууд устгах/нэр солих миграци хориглоно; эхлээд шинийг нэмж, өгөгдөл хуулж, кодыг шилжүүлж, хэд хоногийн дараа л хуучныг устгана.
- Миграци бүрийн өмнө pg_dump backup, restore нь туршигдсан байх.
- Production-ий хуулбар дээр staging орчинд бүх миграцийг эхлээд туршина.
- **Шалгалтын checklist**: миграцийн өмнө/дараа tenant бүрийн гүйлгээ баланс, баланс тайлан, орлогын тайлан, хүснэгт бүрийн мөрийн тоо, касс/бараа/АР/АП-ийн үлдэгдэл ЯГ тэнцэх ёстой. Автомат шалгах скрипт санал болго.
- Downtime байх уу, хэр удаан? Тэг downtime-тай хийх боломжтой юу?
- Миграци бүрт rollback заавар.
- Refactor-ийн явцад SmartGPS-ийн ашиглаж буй бүх функц (MCP tool, API, UI) ажиллагаагаа хадгалах: өөрчлөлт бүрд regression тест.

## 4-р үе шат: Хэрэгжүүлэх дараалал
- Үе шат бүрийг жижиг, тус бүрдээ deploy хийж болох, буцаах боломжтой PR-уудад хуваа.
- Үе шат бүрт: зорилго, өөрчлөгдөх файлууд, миграци байгаа эсэх, эрсдэл, шалгах арга, хугацааны төсөөлөл.
- Хамгийн эхэнд эрсдэл багатай боловч суурь болох ажлуудыг тавь (import-linter, нууц мэдээлэл салгах, DB constraint нэмэх, backup автоматжуулах).
- Хоёрдмол утгатай эсвэл бизнесийн шийдвэр шаардсан зүйл гарвал таамаглалгүй, PLAN.md-ийн "Шийдвэр шаардсан асуултууд" хэсэгт бичээд надаас асуу.
