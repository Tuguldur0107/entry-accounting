| 2 | Банкны хуулга импорт | `app/api/cash/statements/save/route.ts:153-246` | 5,000 хүртэлх мөр хаагдсан сарын GL-ийг бөөнөөр өөрчилнө |

Мөн: зардлын хуваарилалт нь **хуваарилалтын огноог** л шалгадаг тул нээлттэй сард огноолсон allocation хаагдсан сарын орлогын баримтад наалдаж тухайн хаагдсан сарын дундаж өртгийг өөрчилнө (`lib/actions/cost-allocation.ts:179` → `lib/costing/period-run.ts:131-145`). Энэ нь docs/cost OD-011-ийн "хаагдсан сарын allocation rejected" гэсэн мэдэгдлийг зөрчинө.

### K2. GL server action-д мөрийн validation бүхэлдээ client-side

`lib/actions/gl.ts:301-362, 552-614, 364-401`:

- Дансны existence/enabled шалгалт **байхгүй** — дурын текст `accountNumber` болж орно (Excel импорт, AR/AP, AI tools шалгадаг; харин үндсэн Server Action — жинхэнэ trust boundary — шалгадаггүй)
- Debit XOR credit mutex server дээр байхгүй — нэг мөрөнд хоёулаа > 0 байж болно
- Сөрөг дүн зөвшөөрөгдөнө — `{debit:100, credit:-100}` + `{debit:-100, credit:100}` гэсэн voucher ΣDr=ΣCr=0 тул balance шалгалт давж **postгдоно** (спекийн "ΣДебет = 0 → хориотой" дүрэм server дээр огт байхгүй)

`abs(ΣDr−ΣCr) ≤ 0.01` шалгалт өөрөө server дээр зөв хэрэгжсэн (gl.ts:320-325, 375-378, 570-575).

**Засвар:** Нэг shared validator (данс enabled + Dr XOR Cr + дүн ≥ 0 + ΣDr > 0) бичээд create/update/post/import дөрвөн замд дуудах.

### K3. Ашиглагдсан данс шалгалтгүй устдаг

`lib/actions/gl.ts:62-69` — `deleteAccount` нь зөвхөн id+userId-аар устгана. `journal_lines.accountNumber` FK-гүй текст тул жилийн бичилттэй данс устгахад: тайланд нэргүй мөрүүд гарна, тухайн дансаар шинэ бичилт/буцаалт бүгд унана. UI стандартад "Ашиглагдсан данс устгах → анхааруулна" гэсэн ч server юу ч шалгадаггүй (AI/MCP-ээс ч хүрч болно).

**Засвар:** journal_lines + тохиргооны хүснэгтүүдэд (cash_accounts, counterparties, costing_*_settings, inventory_issue_types, fixed_assets) хэрэглээ байвал устгалыг хориглож "идэвхгүй болгох"-ыг санал болгох.

### K4. Migration-ийн төлөв найдваргүй

`lib/db/migrations/` — `0013_*`, `0014_*` давхардсан дугаартай; 4 файл `meta/_journal.json`-д бүртгэлгүй; ~20 хүснэгт (accounting_periods, costing/production бүгд, oauth_*, api_tokens, externalRef unique index гурав г.м.) **ямар ч migration файлгүй** — зөвхөн `drizzle-kit push`/гар SQL-ээр live DB дээр үүссэн. Шинэ орчин migration-аас босохгүй; idempotency-ийн unique index production дээр үнэхээр байгаа эсэхийг батлах баримт байхгүй.

**Засвар:** Schema-гаас цэвэр DB босгож `drizzle-kit generate`-ээр нэгтгэн дугаарлалт засаад цаашид ганц механизм (migrate) хэрэглэх.

### K5. next-auth / @auth/core critical CVE

`npm audit`: getToken uncaught exception, email homoglyph bypass, OAuth state/PKCE cookie provider binding — **`npm audit fix`-ээр засагдана** (breaking биш). Нийт 24 эмзэг байдал (sharp/next high нь Next 16.3.0 шинэчлэлтээр).

## 🟠 ӨНДӨР

### Ө1. Costing: сөрөг хаалтын үлдэгдэл ЗОГСДОГГҮЙ
`lib/costing/periodic.ts:206-210` — зөвхөн сөрөг *available* блоклогдоно; `outbound > available` үед closingQty сөрөг болж статус нь `calculated` хэвээр, сөрөг C2 дараа сар руу дамжина. docs/cost-ийн "юу ч үнэлэгдэхгүй зогсоно" амлалт биелдэггүй. Хүрэх зам: transfer-ээр ирсэн нөөц (period-run.ts:31 valuation-аас хасагддаг) + production confirm (Ө2). Тест ч алга.

### Ө2. Production confirm — negative-stock шалгалтгүй, буруу агуулах
`lib/actions/production.ts:563-581` — input зарлагыг `findNegativeStock` дуудалгүй, `confirmInventoryMovement`-ээс өөр advisory lock-той (4 vs 1), шууд `confirmed` статустай insert хийнэ. Бас inputs-ийг `run.outputs[0].warehouseId`-аас гаргадаг (кодонд "v1 shortcut" гэсэн comment) — батлагдаагүй шийдвэр кодонд нуугдсан.

### Ө3. Production input → COGS fallback = өртөг ДАВХАРДАНА
Production input хөдөлгөөн `issueTypeId`-гүй үүсдэг → post үед `defaultIssueType` (item_cogs) fallback (`lib/actions/costing.ts:376-382`) → `Dr COGS / Cr Нөөц`. Гэтэл яг энэ өртөг output бүтээгдэхүүний капитализацид (production.ts:605-623) орсон байдаг — зарлага P&L-д шууд + бэлэн бүтээгдэхүүнээр дахин COGS. JPR §7.1-ийн `Dr Production/WIP` шаардлага зөрчигдөнө.

### Ө4. Costing-д hardcoded fallback данс
`lib/actions/costing.ts:336-337` — `costing_item_settings` байхгүй бараанд `"14000001"` / `"61100000"` тогтмолоор бичигдэнэ. "Дансны дугаар кодод хатуу бичихийг хориглоно" дүрмийн шууд зөрчил. Мөн cash settlement-ийн FX gain/loss данс hardcoded: `lib/actions/cash.ts:548` (`51800001`/`87000003`).

### Ө5. AI 10M₮ лимит валютын дүнгээр шалгагддаг
`lib/ai/tools.ts:1574-1580` (create_arap_invoice), `:1730-1738` (create_cash_transaction), `:3471-3475` (pay_arap_document) — 9,000 USD (~31M₮) нэхэмжлэх `9000 > 10M = false` тул шууд postгдоно. Post-existing tools нь зөв (`baseAmount`) тул зөрчилтэй. **Засвар:** лимит харьцуулахын өмнө `amount × exchangeRate`.

### Ө6. Delete tools батлагдсан баримтыг ЛИМИТГҮЙ устгана
`lib/ai/tools.ts:2062-2066` г.м. 5 delete tool — post горимд `assertPostLimit`-гүйгээр батлагдсан баримт hard-delete хийнэ. 10M-аас дээш батлах/буцаахыг хориглодог мөртлөө 500M₮-ийн posted voucher-ийг устгаж болно; CLAUDE.md §9a + system-prompt хоёул "зөвхөн ноорог" гэж бичсэн нь кодтой зөрчилдөнө. **Засвар:** posted-delete-д `assertPostLimit` нэмэх эсвэл draft-only болгож баримтжуулалттай нийцүүлэх.

### Ө7. Race conditions (TOCTOU)
- **Close vs Post:** `assertPeriodOpen` бүх замд транзакцийн ГАДНА уншигддаг; `closePeriod` (periods.ts:142-171) lock-гүй — batch post (100 баримт) явж байхад хаалт хийвэл хаагдсан сард posted бичилт орно. **Засвар:** per-user advisory lock-ыг close + бүх post замын транзакц дотор авах, эсвэл период шалгалтыг транзакц дотор давтах.
- **Post vs Update:** `postVoucher` (gl.ts:364-401) мөрүүдээ транзакцийн гадна уншиж balance шалгаад дараа нь claim хийдэг — завсарт `updateVoucher` мөрийг тэнцээгүй болгож сольж болно → тэнцээгүй posted voucher. **Засвар:** claim транзакц дотор мөрөө дахин уншиж шалгах.
- **Delete race:** `deleteVoucher` (gl.ts:624-653) статус уншилт ба устгалын хооронд draft→posted шилжвэл период/subledger шалгалтгүй устгана.

### Ө8. Hot path-д index байхгүй
Schema-д unique-ээс өөр index бараг алга (ai_messages-ийнх л бий). Дор хаяж: `journal_vouchers(user_id, date)`, `journal_lines(voucher_id)`, `journal_lines(cost_entry_id)`, `journal_lines(inventory_movement_id)`, `cash_documents(user_id, status)`, `ar_ap_documents(user_id, status)`, `inventory_movements(user_id, status)`, `ar_ap_settlements(cash_document_id)`. Одоо тайлан бүр хэрэглэгчийн бүх voucher+line-ийг seq scan-аар уншдаг — өгөгдөл өсөхийн хэрээр шугаман удаашрана. Нэг migration-аар шийдэгдэнэ.

## ✅ Зөв хийгдсэн нь (батлагдсан)

- **Tenant isolation бүрэн** — бүх server action, бүх 69 AI tool query userId-аар шүүгдсэн; cross-tenant зам олдоогүй. `runAsUser`/AsyncLocalStorage зөв, concurrent leak боломжгүй
- **OAuth 2.1/MCP** — sha256 hash, PKCE S256 заавал, code нэг удаагийн, refresh rotation, redirect_uri exact match, open redirect хамгаалалт
- **SQL injection, XSS, SSRF олдоогүй**; API түлхүүр AES-256-GCM, bcrypt cost 12
- **Atomic status claim** (`UPDATE … WHERE status='draft'`) бүх post/reverse замд — double-post боломжгүй; settlement overpayment транзакц доторх conditional UPDATE-аар жинхэнэ утгаараа блоклогдсон
- **PWA хөдөлгүүр** спекээ нарийн дагасан: нэг л дундаж, үнэгүй орлого дундажид оролцохгүй, blocked propagation, re-run бүрэн цэвэрлэгээтэй; allocation largest-remainder-ээр яг тэнцдэг; valuation ганц эх сурвалжтай
- **Тайлан posted-only**, reversal хосууд зөв цэвэрлэгддэг; Excel импорт мөр бүрээр дахин шалгадаг; externalRef idempotency schema түвшинд partial unique index-тэй
- FX settlement-ийн 4 тохиолдлын математик зөв; период/timezone логик (Asia/Ulaanbaatar, PTD/QTD/YTD) зөв
